# 統合レビューパイプライン (Full Review Pipeline)

## このスキルの役割

3つの専門レビューを固定順序で適用し、1本の統合レポートを返す。

順序とその理由:
1. **目的定義**(purpose-definition-review)— 目的が壊れていると、以降のすべての評価基準が定まらない。
2. **目標カスケード**(goal-cascade-review)— 構造が壊れていると、情報の要不要が判定できない。
3. **端的さ・情報設計**(concision-review)— 目的と構造が確定して初めて、過不足と負荷を正しく判定できる。

この順序を崩すと「後で目的を直したら、直した構成も全部やり直し」という手戻りが起きる。

## 実行原則(固定プロトコル)

このスキルは、実行するモデルの能力に依存せず同品質のレビューを出すために、実行順・ゲート・統合をアルゴリズムとして固定してある。実行モデルは以下を厳守すること:

1. フェーズの省略・順序変更をしない(対象外スキップの条件を除く)。
2. サブスキルのSKILL.mdをロードしたら、**そのStep 0が指定するreferences(failure-patterns / worked-example 等)も必ず読む**。サブスキル側の全手順・セルフチェック・アンチパターン禁止事項はこのパイプライン内でも全て有効。
3. ゲート判定は下記のアルゴリズム通りに行う。「Criticalだが軽そうだからフル実行」等の裁量を加えない。
4. 出力前にセルフチェックを実施する。

## 実行手順

### Step 0: 対象の確認
レビュー対象の文書と、分かるなら主読者を確認する。文書が無ければ受け取る。読者が不明でも止めない(端的さフェーズで推定する)。

### Step 1: サブスキルのロード(機械手順)
3つのサブスキル名: `purpose-definition-review` / `goal-cascade-review` / `concision-review`

各スキルについて見つからない場合はエラーメッセージを出力させ、ユーザーに対象のサブスキルを用意させる。

### Step 2: ゲート変数の初期化とフェーズ実行

```
phase2_mode = "full"
phase3_mode = "full"

【Phase 1: 目的定義】 purpose-definition-review を常にフル実行する。
c1 = Phase 1 のCritical件数
if c1 >= 1:  # 目的ゲート発動
    phase2_mode = "overview"
    phase3_mode = "overview"

【Phase 2: カスケード】 対象外条件に該当すればスキップ、それ以外は phase2_mode で実行。
c2 = Phase 2 のCritical件数
if c2 >= 1 and phase3_mode == "full":  # 構造ゲート発動
    phase3_mode = "overview"

【Phase 3: 端的さ】 phase3_mode で実行。
```

**対象外条件**(Phase 2のみ): 文書に目標→行動の構造が本質的に含まれない(単純な報告・通知・議事録など)。スキップし、その旨をレポートに注記する。

**ゲートの理由**: 目的が変われば構造も情報選別も変わるため、いま下流の詳細指摘を積んでも大半が無駄になる。全部を並べて情報洪水にすることは、それ自体が著者への認知負荷でありこのスイートの思想に反する。

### 概観モード(overview)の定義 — フェーズごとに実行範囲を固定する

- **カスケード概観**: サブスキルの Step 0〜1(準備・ノード抽出)と Step 3(ツリー構築)のみ実行。再構成ツリーは出す。指摘は重要度上位**3件まで・各3行以内**。十分性テスト・修正版ツリーは出さず、「目的確定後の再レビューで実施」と1行書く。
- **端的さ概観**: サブスキルの Step 0〜3(プロファイル・問いリスト・充足マトリクス)のみ実行。指摘はCritical/Majorの欠落上位**3件まで・各3行以内**。削除候補・認知負荷走査・再構成案は出さず、「目的確定後の再レビューで実施」と1行書く。

### Step 3: 統合レポートの生成(機械手順)

1. **重複マージ**: 「同一の原文引用、または同一のブロック/ノード(P番号・B番号・ツリーノード)」への指摘が複数フェーズにある場合、フェーズ順位【目的(1)> 構造(2)> 情報(3)】の**最小番号**のフェーズに1件として残す。残した指摘の末尾に「(関連: ◯◯観点では△△)」を1行だけ添え、他フェーズ側からは削除する。
2. **上限の適用**: 詳細指摘はフェーズごとに最大5件・全体で15件。超過分は「その他: N件(種別のみ)」。
3. **質問の統合**: 各フェーズの「著者への質問」を全部列挙 → 同じ情報を求める質問を1つにマージ → 通し番号を振り直す。本文中の【要確認: 質問N】参照も新番号に更新する。
4. references/integration-example.md を読み、エグゼクティブサマリとマージの書き方の粒度を合わせる。

## 統合レポートのフォーマット

以下の構造を厳守する。**見出しの追加・削除・順序変更・改名を禁止。**

```
# 統合レビュー: <文書名>

## エグゼクティブサマリ
- 総合判定: (提出可 / 要修正 / 要再設計)+一言
- いま直すべき上位3点(フェーズ横断・効果順)
- ゲート発動の有無とその意味(発動時: 「下流は概観に留めた。目的修正後の再レビューを推奨」)

## フェーズ別サマリ(各3行以内)
1. 目的定義: (実行手段: 専門スキル/簡易チェックリスト)
2. カスケード: (同上。対象外ならその旨)
3. 端的さ: (同上)

## 修正ロードマップ
直す順番と、各ステップで何が解消されるか(必ず 目的→構造→情報 の順)

## 詳細指摘
### 目的定義
### カスケード
### 端的さ
(各フェーズのフォーマットに従う。概観モードのフェーズは「概観モード(◯◯ゲート発動のため)」と明記)

## 著者への質問(統合・重複排除済み)
```

## モード

- **通常**: 上記フル実行。
- **ライト版**: 「軽く見て」「ざっとチェック」と言われたら、各フェーズの判定サマリ+最重要1指摘のみ(合計10行程度)。深掘りすべきフェーズを1つ推奨して終える。
- **個別深掘り**: 統合レポート後に特定観点の深掘りを求められたら、該当する単体スキルに切り替える。

## 出力前セルフチェック(全問Yesになるまで出力しない)

1. レポートは1本か(フェーズごとの長文レポートの連結=ホチキス留めになっていないか)。
2. ゲートの発動状態とその意味がエグゼクティブサマリに明記されているか。
3. 詳細指摘はフェーズ≤5件・全体≤15件か。
4. 各フェーズの実行手段(専門スキル/フォールバック)と実行モード(フル/概観)を注記したか。
5. 修正ロードマップが目的→構造→情報の順か。
6. 質問は重複排除・通し番号済みで、本文の【要確認】参照と番号が一致しているか。
7. サブスキルのセルフチェック(原文引用・捏造なし・判定表準拠)を各フェーズで通したか。

## 行動原則

- 良い点も1〜2点書く。ただしお世辞ではなく「ここは崩すな」という保全指示として。
- 全フェーズ通して問題が軽微なら、そう明言して短く終える。レビューの長さで価値を演出しない。
- レビュー中に判明した文書内の具体的な芽(使える数値・具体例)は積極的に拾い、修正の起点として示す。
