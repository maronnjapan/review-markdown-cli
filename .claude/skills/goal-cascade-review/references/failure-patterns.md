# カスケードの失敗パターン集

各パターンは「症状 → なぜ問題か → 検出方法 → 例」。例はフィクションであり、実レビューでは文書内の情報だけで修正案を作ること。

**検出の正式な判定手順(レベル判定質問・接続判定・判定表)は SKILL.md 側にある。本ファイルは症状の理解・パターン名の付与・修正例の型の参照に使う。食い違って見える場合は SKILL.md を優先する。**

## 1. ミッシングミドル(中間層の不在)
- 症状: [G]の直下に[A]がぶら下がる。
- なぜ問題か: 行動の進捗が目標の前進に換算できず、途中で方向の正しさを検証できない。行動を全部終えたのに目標に届かない事故の典型原因。
- 検出: ツリーで[G]→[A]の直結。
- 悪い例:
```
[G] 開発生産性を上げる
 ├─[A] CIのキャッシュを設定する
 └─[A] レビュー会を隔週にする
```
- 修正例:
```
[G] 開発生産性を上げる(PRリードタイム中央値を5日→2日)
 ├─[M1] CI待ち時間が平均20分→5分になっている
 │   └─[A] CIのキャッシュを設定する
 └─[M2] レビュー着手までの待ちが48h→24h以内になっている
     └─[A] レビュー当番制を導入する
```

## 2. 孤児行動(やりたいことリスト化)
- 症状: どの[M]にも接続しない[A]が混ざる。行動が先にあり、目標が後付け。
- なぜ問題か: リソースが目標に効かない作業に流れる。「新しいことを始めたい」が計画に紛れ込む典型経路でもある。
- 検出: 上りテストで「どのMがどれだけ前進する?」に答えられない。
- 対処: (a) 本当に効くなら対応する[M]を明文化する、(b) 効かないなら計画から外す(別案件として退避)。

## 3. 宙吊り目標(スローガン化)
- 症状: [A]が1つも紐付かない[M]。
- なぜ問題か: 掲げただけで動かない目標は、達成しないうえに「やっている感」だけを生む。
- 検出: 下りテストで[A]ゼロ。
- 対処: 最初の一歩の[A]を最低1つ定義するか、今期のスコープ外として明示的に落とす。

## 4. 活動目標(完了判定不能な中間目標)
- 症状: [M]が「〜を検討する」「〜を推進する」「〜に取り組む」で書かれている。
- なぜ問題か: 活動はいつまでも「やっている」と言えるため、達成判定ができない。カスケードの結節点が曖昧だと、上下のトレースも全部曖昧になる。
- 検出: [M]の文末が動作動詞。「それが終わったとき何が成立している?」に答えられるか問う。
- 悪い例: 「[M] 監視の強化を推進する」
- 修正例: 「[M] 全APIエンドポイントにアラート閾値が設定され、擬似障害が10分以内に検知される」

## 5. 抽象度ジャンプ / 粒度混在
- 症状: 同じ階層に「アーキテクチャ刷新」と「READMEのtypo修正」が並ぶ。親子で2段階以上飛ぶ。
- なぜ問題か: 読み手が階層を頭の中で補正しながら読むことになり、認知負荷が跳ね上がる。粒度の小さい項目が大きい項目と同格に見え、工数感も歪む。
- 検出: 抽象度4段階分類(成果状態/中間成果/活動/タスク)で隣接ノードを比較。
- 対処: 小粒度の項目は近い[M]の下に格下げ、または[M]を新設して束ねる。

## 6. 因果の願望(やればきっと効く)
- 症状: [A]→[M]、[M]→[G]の矢印が根拠なき期待で繋がれている。
- なぜ問題か: 仮定が明示されていないと、外れたときに計画のどこを直せばいいか分からない。仮定の明示は弱さではなく検証可能性。
- 検出: 矢印に「なぜそう言える?」と問うて文書内に根拠がない。
- 対処: 「? 仮定: ...」を付けて可視化し、可能なら早期に仮定を検証する[A](小さな実験・計測)の追加を提案する。

## 7. 十分性錯覚(部分カバー)
- 症状: [M]群が[G]の一部領域しかカバーしていないのに、全体を達成できるように見える。
- なぜ問題か: 全部やり切った後で「そもそも足りなかった」が発覚する。最も高くつく失敗。
- 検出: 十分性テスト。「全M達成の世界」を描写して[G]と比べる。
- 例: [G]「技術書の収益化」に対し、[M]が執筆と宣伝のみで、価格設定・販路が空白。全M達成でも「書けて知られているが、売れる導線がない」世界になる。
